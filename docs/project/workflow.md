# 变更流程

> 接手断点 → 需求与验收条件 → 影响分析 → 实现 → 回归 → 文档同步 → 时间轴收尾。任何修改都走这条链，AI 与人类同等适用。

## 0. 接手与断点

- 任务开始：先读 [Handed-docs.md](../Handed-docs.md) 断点区——有在途任务默认续做（用户另有指定除外）；多阶段任务在实质修改前先建断点块（目标、验收标准、基线 commit、初始计划）。
- 里程碑：实现 + 验证完成后**先刷新断点再继续**（触发条件见 [AGENTS.md](../../AGENTS.md)「接手文档」）。
- 断点缺失或与工作区对不上：按 AGENTS.md 灾难恢复协议，先登记实况、建断点块，再动手。

## 1. 需求与验收条件

- 用一句话说清「改什么」，再用可检查的条目说清「怎样算完成」。
- 涉及 UI 的验收条件必须包含：明暗两种模式、目标主题下的可读性（亮黄 / 亮绿 / 青主题重点）、键盘操作、减少动态效果。
- 涉及数据的验收条件必须包含：旧数据（缺字段 / 非法值）打开后的行为。

## 2. 影响分析

- 按 [architecture.md](architecture.md) 判定改动落在哪些层；跨层改动（如新增设置项）列出全部触点。
- 检索同类实现再动手：项目里大概率已有同构代码（设置项、错误条、折叠面板…），先仿照再抽象。
- 明确列出「不改的东西」；发现顺手可改的问题记入待办，不夹带进本次变更。

## 3. 实现

- 遵守 [AGENTS.md](../../AGENTS.md) 硬性约束。
- 修复与新功能的检查重点不同：
  - **修复**：先写一个能复现问题的测试（失败态），再修到通过；核对旧数据路径；确认根因而非症状。
  - **新功能**：先补测试与文档骨架再实现；对外行为（IPC 字段、事件、设置项）成对出现。
- 错误处理遵循 [interfaces-and-compat.md](interfaces-and-compat.md) 的错误规范：给用户可读的中文信息 + 可恢复路径（重试 / 回读），不给裸错误码。

## 4. 回归

按 [testing.md](testing.md) 执行；最低集合：

```bash
pnpm test && pnpm build && (cd src-tauri && cargo test && cargo check) && git diff --check
```

涉及主题 / UI 时额外人工冒烟：切换 7 套主题 × 明暗，覆盖主要按钮、输入框、禁用态、错误提示、弹窗（清单见 [ui-and-themes.md](ui-and-themes.md)）。

## 5. 文档同步

- 行为变化 → 更新对应 `docs/project/` 文档与 README（保持入口链接有效、示例与代码一致）。
- 有取舍的架构决策 → 补一条 ADR（模板见 [decisions.md](decisions.md)）。
- 交付说明按「自动测试 / 人工冒烟 / 未验证」三档记录（模板见 [CONTRIBUTING.md](../../CONTRIBUTING.md)）。
- 任务收尾 → 在 [Handed-docs.md](../Handed-docs.md) 时间轴最上方追加条目（模板在文档内），断点区恢复「当前无在途任务」。
